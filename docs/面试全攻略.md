## Part 1: 30 秒说清项目

### 15 秒版（电梯/开场）

> "我做了一个多 Agent 的自我成长管理系统——AI 帮你排计划、盯执行、给周报复盘，计划改动必须人工审批。"

### 30 秒版（面试官说"展开讲讲"时）

> "用户贴入学习计划或写一句话，教练 Agent 自动拆解科目、排到每天（每天最多 3 件）。用户打卡时如果跳过任务要选原因标签——分心、太难、疲劳还是被打断。复盘师 Agent 每周根据这些数据生成洞察，比如'你 22 点后的任务全跳过了，建议把政治移到下午'。所有计划改动必须用户审批才生效。"

### 三个数字（面试的锚点）

- **3 个 LLM Agent** + 1 个确定性管家（不是 4 个——管家是纯代码零 LLM）
- **87 个测试**双库通过（SQLite + PostgreSQL 16），覆盖率 81%
- **11 轮无偏代码审查**，75 项发现全部当轮修复

### 口径红线（防穿帮）

- 不说"高并发"——关键词是**多 Agent 编排、HITL、代码审查文化**
- 说"图很小（三个节点）是**故意的**"——LangGraph 价值在骨架
- 竞品口径勿混：爬虫项目说"礼貌限速"，本作品说"多 Agent 编排"

## Part 2: 架构与技术栈

### 架构图（含数据流）

```
手机 PWA（今日/对话/档案 三 Tab）
       │ HTTPS（打卡请求：POST /tasks/{id}/complete）
  Caddy 反向代理（自动 HTTPS + 安全头）
       │
  FastAPI 后端
     ├── 教练 Agent ── LangGraph 图（条件边 + 工具循环）
     │      └── 工具：get_goal / schedule_week / submit_proposal
     ├── 复盘师 Agent ── 工具循环（钻取：完成率→卡因→时段）
     ├── 陪练 ── 单次 LLM 调用（错题讲解）
     ├── 管家 ── 零 LLM（APScheduler 晨推/提醒）
     └── PostgreSQL ← 所有 Agent 通过这条共享数据库隐式协作
```

**Agent 间通信**：三个 Agent 不直接对话，通过共享 PostgreSQL 数据库协作——教练写的计划被管家读到生成晨推，管家收集的打卡被复盘师读到生成周报。这是比消息传递更简单也更可靠的方案。

### 技术栈（按层分组）

| 层 | 技术 |
|---|---|
| 后端 | Python 3.12 · FastAPI · SQLAlchemy 2.0 async · Alembic |
| Agent | LangGraph 1.2 · FastMCP 4.0 · OpenAI SDK（BYOK） |
| 数据 | PostgreSQL 16（生产）/ SQLite（开发测试双跑） |
| 前端 | Next.js 16 · React 19 · TypeScript strict · Tailwind v4 · ECharts |
| 运维 | Docker · Caddy · APScheduler · GitHub Actions |

### 四个架构决策

| 决策 | 为什么 | 放弃了什么 | 面试一句话 |
|---|---|---|---|
| PWA 优先 | solo 不做原生 | Expo（1-2 周后可迁） | "API-first 保证迁移只换壳" |
| 只在见机行事处用 Agent | 晨推不需要 LLM | 全 Agent 化（成本×N） | "知道什么时候不用更值钱" |
| HITL 放服务层 | interrupt 跨请求复杂 | LangGraph interrupt | "interrupt 适合插嘴，服务层适合关 App" |
| token 存 localStorage | 当前无 XSS 面 | httpOnly cookie（要 CSRF） | "带触发条件的分期决策" |

## Part 3: Agent 核心概念（面试必问）

### 3.1 LangGraph vs LangChain

**比喻**：LangChain 是流水线（A→B→C 固定顺序），LangGraph 是地铁线路图（有分叉、有换乘、可以折返）。

| | LangChain | LangGraph |
|---|---|---|
| 编排 | 链式（线性） | 图状（节点+边+条件+循环） |
| 适用 | 固定流程 | 有分支/循环/人工介入 |

**我们的选择**：只用 LangGraph——教练需要条件分支和工具循环。

### 3.2 State（贯穿全图的工单）

**比喻**：各站点共用的检修工单，每个工位读它、往上写一笔，下一站拿到的还是同一张单子。

```python
class PlannerState(TypedDict, total=False):
    missing: list[str]              # 路由用：gather 写、条件边读
    parsed_subjects: list[dict]     # parse 写、coach 读
```

**三个关键点**：
1. `TypedDict`：运行时就是普通 dict，LangGraph 读类型标注认识合法字段
2. `total=False`：所有键可选——入口 `ainvoke({})` 可以传空工单
3. **自动合并**：节点返回 partial dict → 框架 merge，不覆盖其他键

> **核心设计判断**：路由要看的数据进 State，干活要用的材料走闭包。
> raw_text 和 backend 走闭包（函数记住外层变量），工单保持干净。

### 3.3 节点（一道工序）

| 节点 | 干什么 | 读 | 写 |
|---|---|---|---|
| `gather` | 查目标缺不缺截止日/时长 | `self._goal`（闭包） | `{"missing": [...]}` |
| `parse` | LLM 解析贴入文本 | raw_text、backend（闭包） | `{"parsed_subjects": ...}` |
| `coach` | **工具循环**（核心） | 闭包 + state | `{}`（产物写进 ctx 闭包对象） |

节点就是函数：`(state) -> partial dict`，同步异步均可。

### 3.4 边（流向控制）

**固定边** `add_edge(A, B)`：传送带，A 干完必去 B。

**条件边三件套**（面试最常问）：

```python
# ① 起点：从哪个节点分流
# ② 路由函数：吃 state，返回"下一站的名字"
def has_questions(state) -> str:
    return "questions" if state.get("missing") else "parse"

# ③ 映射表：名字 → 真实目的地
graph.add_conditional_edges("gather", has_questions,
    {"questions": END, "parse": "parse"})
```

```
START → gather ─┬─ 缺信息 → END（返回追问，LLM 零调用）
                └─ 信息齐  → parse → coach → END（提案待审批）
```

**如果追问**：
- *"路由函数返回的名字不在映射表里？"* → LangGraph 抛出错误（图不完整）
- *"不传映射表行不行？"* → 可以，路由函数直接返回节点名
- *"返回 list 做并行分发？"* → 可以（LangGraph 支持返回列表触发多个下游节点）

### 3.5 Checkpoint 与 interrupt

**Checkpoint** = 把图运行状态持久化（像游戏存档），用于中断恢复、故障恢复。

**interrupt()** = 在节点内挂起等人 → checkpointer 存状态 → `Command(resume=value)` 恢复。

**我们为什么不用**（ADR-0003，面试杀手锏 #3）：

| 维度 | interrupt 方案 | 我们的服务层方案 |
|---|---|---|
| 跨请求 | 需要 AsyncPostgresSaver + 跨请求会话管理 | plan_proposals 表 + 条件 UPDATE |
| 重启 | 持久化 Saver 不丢（但配置更重） | **天然免疫**（数据在 DB） |
| 复杂度 | 节点闭包持有 DB 会话，跨请求已关闭 | 确定性 SQL，零额外状态 |

> **面试金句**："interrupt 适合'对话中插一嘴'，服务层审批适合'关掉 App 明天再批'。知道什么时候不用一个技术和会用它同样重要。"

**如果追问**："对话中途用户要补充信息怎么办？"
> **诚实回答**："目前要求用户重新发起请求补全信息。这是已知限制，如果做对话 Tab 会引入 AsyncPostgresSaver + thread_id 做多轮接续——这是 P2 的规划。"

### 3.6 工具循环（ReAct 模式）——Agent 性的核心

**比喻**：新来的助理帮你订会议室——他自己"查日历→发现冲突→查替代→发确认"，工具是他的手和脚。

**消息流**（教练的一次完整运行，序号对应"Agent 性"出现的位置）：
```
[system 规则] → [user 目标+原文]
→ ①调 get_goal_context       ← 模型自己决定的
→ ②调 schedule_week(18h)
→ 工具返回 overloaded=true!
→ ③模型自己下调，再调 schedule_week(10h)  ← Agent 性在这里！
→ ④调 submit_proposal → 提案落库
```

**核心代码**（面试时能手画的循环）：
```python
for _ in range(6):                                # 上限 6 轮
    result = await backend.complete(messages, tools)
    if not result.tool_calls: break               # 模型不调了 = 收工
    messages.append(含 tool_calls 的助手消息)
    for call in result.tool_calls:
        try:
            data = await client.call_tool(call.name, call.arguments)
        except Exception:
            logger.exception("工具 %s 失败", call.name)
            data = {"error": "工具执行失败，请检查参数后重试"}
        messages.append({"role": "tool", "content": json.dumps(data)})
    if ctx.proposal_id is not None: break         # 提案落地 = 出循环
```

**关键设计点**：
- **错误回喂**：工具失败不 500，包装成 `{"error": ...}` 作为 tool 消息回传给模型自行纠正
- **为什么 6 轮**：4 个工具 + 提交，正常路径 3-4 轮；留 2 轮余量给自纠偏（如超载重排）
- **Agent 性在第③步**：看到超载后下调多少、要不要再排——是模型临场决定的

### 3.7 MCP（Model Context Protocol）

**比喻**：USB-C 接口——模型是设备，工具是外设，MCP 是统一接口标准。FastMCP 进程内调用 = 焊在主板上的外设（零序列化开销）。

**为什么需要 MCP**（不是"因为它是开放标准"）：
- 没有 MCP：每个 AI 应用 × 每个工具 = N×M 次重复造轮子
- 有了 MCP：工具写一次（MCP Server），任何支持 MCP 的客户端都能用

**和 Function Calling 的区别**：Function Calling 是厂商私有 API 格式，MCP 是跨厂商开放标准。

**我们的用法**：FastMCP 4.0，进程内 Client 调用零网络。工具只调 repository 层（和前端按钮同一条被测试覆盖的写入路径）。

**如果追问**："既然进程内零网络，为什么还要 MCP？直接调 Python 函数不更简单？"
> "三个理由：①统一注册成带 JSON Schema 的工具，LLM 看到标准化描述；②将来换对话型 Agent 或接入外部客户端，工具层直接复用；③MCP 的发现机制让工具列表可枚举、可测试。"

### 3.8 HITL 与权限模型（安全跟着审批讲）

### Prompt 注入防御四层

| 层 | 防什么攻击 | 怎么防 |
|---|---|---|
| ① 输入隔离 | 攻击文本冒充指令 | 只进 user message，8000 字截断，定界符包裹 |
| ② 工具无用户参数 | 诱导 Agent 越权写别人数据 | 写入全绑定 ctx.goal（启动时鉴权） |
| ③ 输出过校验 | 塞入超量/非法数据 | ≤50 条/时长 1-240/日期合法 |
| ④ HITL 兜底 | 绕过所有防线直接生效 | 产物 DRAFT 态必须人审 |

### 写权限矩阵（比喻：门禁卡）

| 数据 | Agent 权限 |
|---|---|
| 查询（读） | 自由（大堂） |
| 计划 | 起草 → 人审 → 落库（访客登记） |
| 历史事实 | **永不可写**（保险库） |
| 密钥/账号 | 不可写（机房） |

> **面试金句**："Agent 可以修改未来的安排，不能篡改过去的事实。"

## Part 5: 工程实践与踩坑故事

### 审查文化（杀手锏 #2 的展开）

**无偏审查是什么**：每完成一个里程碑，启动一个**不带项目上下文的独立 AI 审查员**——只给它中性产品规格，不给设计理由和辩护词。11 轮共 75 项发现。

**为什么 87 个测试拦不住 P0**：三类原因——
1. **环境差异**（httpx 在 dev extras 但生产需要——本地和 CI 都装了全部 extras，掩盖了基础安装缺失）
2. **时序问题**（Promise 毒化——异步刷新失败后 rejected Promise 被缓存，后续所有 401 恢复永久失效）
3. **数据条件**（离线补传 401 丢队列——只在"断网超 15 分钟 + token 过期"的组合条件下触发）

### 踩坑精选（每个都是四段式故事）

**坑 1：httpx 依赖位置**
- 现象：Docker 镜像启动报 `ModuleNotFoundError: httpx`
- 根因：httpx 写在 `[dev]` extras，但生产代码 `import httpx`——基础安装不装 extras
- 修复：移入主 dependencies
- 教训：**生产依赖和生产代码必须在同一层**

**坑 2：Promise 毒化**
- 现象：一次网络闪断后，整个会话的 401 恢复永久失效
- 根因：`refreshing = refreshing ?? doRefresh()` 后 `await refreshing` 抛异常 → `refreshing = null` 被跳过 → 模块级变量永久持有 rejected Promise
- 修复：`try { await refreshing } finally { refreshing = null }`
- 教训：**异步单例必须有 finally 清理**

**坑 3：fastmcp 函数名遮蔽**
- 现象：mypy 报"Coroutine 没有 capacity_minutes 属性"
- 根因：`@mcp.tool` 装饰的 `schedule_week` 与导入的算法函数**同名**，函数体内调的是装饰后的包装器
- 修复：`from ... import schedule_week as run_scheduler`
- 教训：**装饰器改变名字绑定，命名先查导入区**

**坑 4：SQLite vs PG 时间**
- 现象：通知去重在北京 07:00 与 UTC 前一天 23:00 之间判断不一致
- 根因：SQLite 存朴素 UTC 字符串，PG 存 timestamptz——直接比较两种引擎行为不同
- 修复：`cn_day_start_utc_naive()` 统一用朴素 UTC 比较
- 教训：**跨库时间比较要么全 aware 要么全朴素 UTC**

## Part 6: 三个面试杀手锏

### #1: 三种编排粒度（有数字版）

| 教练（图） | 复盘师（循环） | 陪练（单次） |
|---|---|---|
| 4 工具，3-5 轮 | 4 工具，2-3 轮 | 0 工具，1 轮 |
| ~15-30 秒 | ~10-20 秒 | ~3-5 秒 |

> "粒度递减因为 Agent 性需求递减。我选编排方式的决策框架是：有分叉用图、纯线性用循环、一次够用就直接调。"

### #2: 11 轮审查 75 项全修

> "每完成一个里程碑自动跑无偏审查——75 项全修，含 3 个 P0。最有价值的是**测试拦不住 P0 的三类原因**：环境差异、异步时序、数据条件——这是我在真实工程里学到的测试局限性认知。"

### #3: ADR-0003 不用 interrupt

> "我评估过 AsyncPostgresSaver + thread_id 方案——技术上可行，但节点闭包持有 DB 会话跨请求已关闭，需要重构会话管理。改为服务层条件 UPDATE，一个原子操作解决并发双批问题。**interrupt 适合'对话中插一嘴'，服务层审批适合'关掉 App 明天再批'。**"

<details><summary>答案</summary>链式 vs 图状。我们只用 LangGraph 因为需要条件分支和工具循环。</details>

**Q2: State 怎么定义？** → [3.2](#32)
<details><summary>答案</summary>TypedDict + total=False，节点返回 partial dict 自动 merge。路由数据进 State，材料走闭包。</details>

**Q3: 节点是什么？** → [3.3](#33)
<details><summary>答案</summary>函数，签名 (state) → partial dict，同步异步均可。</details>

**Q4: 条件边怎么工作？** → [3.4](#34)
<details><summary>答案</summary>三件套——①起点 ②路由函数（吃 state 返回名字）③映射表（名字→目的地）。</details>

**Q5: Checkpointing 是什么？** → [3.5](#35)
<details><summary>答案</summary>持久化图运行状态，用于中断恢复。我们用服务层 plan_proposals 替代。</details>

**Q6: HITL 怎么实现？** → [3.5](#35)
<details><summary>答案</summary>LangGraph 用 interrupt()/resume。我们用服务层条件 UPDATE——重启免疫、并发安全。</details>

**Q7: 单 vs 多 Agent？** → [4](#part-4)
<details><summary>答案</summary>三个理由（上下文隔离/独立测试/不同工具集）。判断：下一步是否临场决定。</details>

**Q8: Supervisor 模式？** → [4](#part-4)
<details><summary>答案</summary>设计过（ADR-0002），当前用确定性路由替代。如果对话复杂度上来值得引入。</details>

**Q9: ReAct 是什么？** → [3.6](#36)
<details><summary>答案</summary>推理→行动→观察→再推理循环。教练超载自调重排就是 ReAct。</details>

**Q10: LangGraph vs CrewAI vs AutoGen？** → [4](#part-4)
<details><summary>答案</summary>LangGraph 低级精细、CrewAI 高级角色、AutoGen 对话式。我们选精细控制。</details>

**Q11: MCP 和 Function Calling 区别？** → [3.7](#37)
<details><summary>答案</summary>MCP 是跨厂商开放标准（USB-C），Function Calling 是厂商私有。我们用 FastMCP 进程内。</details>

**Q12: MCP 安全风险？** → [3.8](#38)
<details><summary>答案</summary>恶意 Server 注入、工具越权。防御：权限矩阵 + 输出校验 + 工具只调 repository。</details>

**Q13: 怎么防 Prompt 注入？** → [3.8](#38)
<details><summary>答案</summary>四层——输入隔离/工具无用户参数/输出校验/HITL 兜底。</details>

**Q14: Agent 幻觉？** → [3.6](#36)
<details><summary>答案</summary>排程用确定性算法（LLM 不做算术）、数据来自 SQL、提交前校验快照非空。</details>

**Q15: Function Calling 底层？** → [3.6](#36)
<details><summary>答案</summary>工具定义（JSON Schema）→ 模型返回 tool_calls → 执行 → role="tool" 回传 → 循环。</details>
