# ADR-0002：Agent 边界——只在需要"见机行事"处用 Agent

日期：2026-09-23 · 状态：已采纳

## 背景

产品最初设想 4 个 LLM Agent（规划/执行/复盘/学习）。外部无偏评测指出：把确定性工作包装成 Agent 只增加成本、延迟与故障面；"为什么需要四个 Agent"在面试中经不起追问。

## 决策

- **LLM Agent 仅三个**：总编（意图路由）、教练（计划对齐与调整提案）、复盘师（数据钻取与周报洞察）；
- **管家降级为确定性代码**：晨推 = 模板 + SQL（零 LLM 调用），打卡/统计/streak 同理；
- **前端不展示多 Agent 概念**（无"团队动态"Tab），架构叙事保留在 README 与本文档。

## 判定标准

一个环节交给 Agent，当且仅当它满足：下一步动作依赖上一步结果、无法预先写成固定流程。反例：晨间摘要（固定查询+模板）。正例：复盘师发现周三完成率异常 → 自主决定钻取卡因 → 再钻时段分布。

## 安全边界（与写权限矩阵配套）

- 查询自由；事实记录直写；**计划类改动必须 HITL 审批后落库**；
- **历史事实（打卡/卡因）任何情况下不可改写**；
- LLM 输出一律经 Pydantic schema 校验，永不直接执行；
- 计划版本化（可回滚）+ 全量审计日志。

## 被否方案

- 四 Agent 全 LLM 化：成本 ×N、可靠性下降、面试叙事弱；
- 完全无 Agent（纯模板系统）：失去主动干预与"它懂我"洞察，产品退化为待办清单。
