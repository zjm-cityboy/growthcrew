## 一、LangGraph 核心（占比最高）

### Q1: LangGraph 和 LangChain 的区别？

**答**：LangChain 是链式编排（prompt → model → parser），适合线性 LLM 应用；LangGraph 是图状编排（节点+边+条件路由+循环+状态），适合有分支/循环/人工介入的 Agent。

**我们的代码**：只装 langgraph 没装 langchain——教练需要条件分支和工具循环，这是图状模式。

### Q2: StateGraph 里的 State 怎么定义？

**答**：State 是贯穿全图的共享数据结构。用 TypedDict（加 `total=False` 让字段可选），节点返回 partial dict 自动 merge。

**我们的代码**：三键 TypedDict，路由用 `missing`，干活用 `parsed_subjects`。**路由看的数据进 State，材料走闭包**。

### Q3: 节点是什么？同步还是异步？

**答**：节点就是函数：`(state) -> partial dict`，同步异步均可。不是类不是特殊对象。

**我们的代码**：gather 同步（读内存）、parse/coach 异步（调 LLM）。

### Q4: 条件边怎么工作？（面试最常问）

**答**：三件套——①起点（从哪分流）②路由函数（吃 state 返回"下一站名字"）③映射表（名字→目的地）。

**我们的代码**：
```python
def has_questions(state) -> str:
    return "questions" if state.get("missing") else "parse"
graph.add_conditional_edges("gather", has_questions, {"questions": END, "parse": "parse"})
```

### Q5: Checkpointing 是什么？

**答**：把图运行状态持久化（当前节点/State/消息），用于中断恢复、故障恢复、时间旅行调试。

**我们的选择**：**没用**——图在单次 HTTP 内跑完，审批在服务层（plan_proposals 表 + 条件 UPDATE）。

### Q6: HITL 在 LangGraph 里怎么实现？

**答**：节点内 `interrupt()` 挂起 → checkpointer 存状态 → `Command(resume=value)` 恢复。

**我们的选择**：服务层审批而非 interrupt——跨请求保存图状态需要跨请求会话管理，复杂度不成比例。**interrupt 适合"对话中插一嘴"，服务层审批适合"关掉 App 明天再批"。**

## 二、Agent 设计模式

### Q7: 什么时候单 Agent vs 多 Agent？

**答**：多 Agent 的三个理由——①上下文隔离（干净窗口）②独立测试 ③不同模型/工具集。不是越多越好。

**我们的代码**：3 个 LLM Agent + 1 个确定性管家。判断标准：**下一步是否依赖上一步临场决定**。

### Q8: Supervisor 模式？

**答**：中央 Agent 接收输入→分派给专业 Agent→汇总返回。与 P2P 的区别：集中控制 vs 直接对话。

**我们的代码**：总编是 Supervisor，路由给教练（计划类）或复盘师（数据类）。

### Q9: ReAct 模式？

**答**：Reasoning + Acting 循环——LLM 思考→调工具→看结果→再思考→直到得出答案。LangGraph/LangChain/CrewAI 核心都是 ReAct。

**我们的代码**：教练看到排程超载→自调→重排，走哪条工具路径是模型临时定的。

## 三、框架对比

### Q10: LangGraph vs CrewAI vs AutoGen？

| | LangGraph | CrewAI | AutoGen |
|---|---|---|---|
| 抽象 | 低级（图原语） | 高级（角色/任务） | 中级（对话式） |
| 控制 | 最精细 | 声明式 | 协商式 |
| 适用 | 需要精细控制 | 快速搭建 | 研究型 |

**我们选 LangGraph**：需要条件分支、工具循环、与 FastMCP 深度集成。CrewAI 角色抽象太重，AutoGen 对话式不需要。

## 四、MCP 协议

### Q11: MCP 是什么？和 Function Calling 区别？

**答**：MCP = Model Context Protocol，Anthropic 开源标准化协议。Function Calling 是厂商私有 API 格式（OpenAI/Anthropic 各不同）；MCP 是跨厂商开放标准——一个 Server 写一次，任何客户端都能用。

**我们的代码**：FastMCP 4.0 注册教练/复盘师工具，进程内 Client 零网络。

### Q12: MCP 安全风险？

**答**：恶意 Server 注入 prompt / 工具越权 / 数据中转泄漏。

**我们的代码**：权限矩阵（读自由/计划HITL/历史永不可写）+ 输出过校验 + 工具只调 repository。

## 五、安全与可靠性

### Q13: 怎么防 Prompt 注入？

**答**：四层——输入只进 user message + 定界符；工具无用户参数；输出过 schema 校验；HITL 兜底。

**我们的代码**：贴入文本 8000 字截断、工具全绑 ctx.goal、≤50条/时长1-240/日期合法、DRAFT 必须人审。

### Q14: Agent 幻觉怎么处理？

**答**：结构化输出 + 工具返回真实数据 + RAG + HITL。

**我们的代码**：排程是确定性算法（LLM 不做算术）、周报数据来自 SQL（LLM 只把数字变人话）、submit_report 硬校验快照非空。

## 六、工具调用

### Q15: Function Calling 底层原理？

**答**：应用把工具定义（JSON Schema）发给模型 → 模型返回 tool_calls（函数名+参数）→ 应用执行 → 结果以 role="tool" 回传 → 模型继续推理或再调。

**我们的代码**：手动维护消息循环，工具 Schema 从 FastMCP list_tools() 动态获取。
